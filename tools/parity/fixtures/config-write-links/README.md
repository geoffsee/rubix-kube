# Configuration writer link and failure characterization

This is a bounded E02.02 oracle supporting E03.03 (#41). It calls the actual
`internal/config.Write` from KubeSolo revision
`2ef1c4787989f11f868f81bb84ae2afd4a49a81d`. The only source-copy addition is
`file_capture_test.go`; the vendored reference stays unchanged.

Seven cases run twice in separate disposable, unprivileged containers: destination
symlink, backup symlink, backup hard link, preexisting permissive backup,
destination directory, backup directory, and ordinary replacement. Each case owns
its temporary directory, and all link targets are inside that directory. No host
mounts, host credentials, host configuration writes, or privileged containers are
used. Cases use umask 0000 to isolate existing modes and link behavior; the earlier
`../config-api` oracle separately characterizes restrictive umask.

Observed Go behavior:

- Destination symlink: its referent's exact old bytes become the backup, the
  referent remains unchanged, and the symlink entry becomes a new regular 0600 file.
- Backup symlink: the link survives and its referent is truncated/replaced with
  the old configuration bytes. The referent keeps its existing 0644 mode.
- Backup hard link: both names still identify the same inode; both now expose
  the old configuration bytes, retaining 0644 mode.
- Preexisting ordinary 0644 backup: overwritten without narrowing permissions.
- Destination or backup directory: error; destination inode and contents/type
  remain unchanged; no temporary file remains.
- Ordinary replacement: new destination inode, target and fresh backup 0600;
  backup preserves comments and original bytes exactly.

These are observations, not a recommendation to reproduce unsafe backup writes.
Publishing a new 0600 backup through a separate temporary file and rename would
intentionally stop following existing backup links and stop modifying their
referents. The baseline's destination-symlink behavior is distinct and needs its
own documented policy if changed. No cross-process locking, adversarial directory
replacement, crash recovery, power-loss durability, or arbitrary filesystem fault
coverage is claimed.

`verify.py` independently constructs exact expected names, types, modes, contents,
link text, success/failure, and inode relationships from the reviewed writer's
operations. Expected replacement YAML comes from the earlier independently
captured `config-api/config.json` first document with the identical synthetic
credential; it is not generated by the writer being tested here. `provenance.json`
binds that input and all local sources/evidence. The verifier rejects extra staging
entries and compares JSON with strict boolean/integer distinctions. Raw log records
and JSON files share a bounded strict parser that rejects duplicate keys, nonfinite
constants and floating-point overflow. JSON and capture logs have a 1MiB read limit.
The command verifier requires the complete receipt, both successful run records,
current driver/verifier/harness/input hashes, exact pinned source identity, raw-log
digests, raw-to-normalized record equality, and verified empty cleanup inventories.
The frozen-evidence test additionally requires the complete local/source hash
inventories and binds replacement YAML to its earlier config-api oracle. Mutation tests
reject failed/missing runs, missing provenance entries, stale hashes and tampered
raw or normalized records, including under `python -O`, and cover each consequential link, mode, failure, byte preservation and cleanup claim.

```sh
python3 tools/parity/fixtures/config-write-links/capture.py --output /tmp/unique-writer-links
python3 tools/parity/fixtures/config-write-links/verify.py /tmp/unique-writer-links
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/parity/fixtures/config-write-links -p 'test_*.py'
```

The builder image, source archive, and revision are pinned in `Capture.Dockerfile`.
Build timeout is 30 minutes. Each trusted finite seven-case test run has a 90-second
Go timeout, 110-second Docker deadline, 512MiB memory, 128 PID limit, two CPUs,
private 64MiB temporary filesystem, read-only root, no network, no capabilities,
and no-new-privileges. File output and streamed test logs are limited to 1MiB; streamed build logs
are limited to 16MiB. A deadline or output-budget failure kills/reaps the client
process before owned Docker resource cleanup. This runner executes trusted pinned
source tests, not hostile submitted executables. Cleanup
independently removes and inventories owned containers/images, always attempts a
receipt, and treats unknown inventory as failure. Ordinary build cache remains.

`reference.json` is the first successful final run; `evidence/repeat.json` retains
the second identical run. The receipt binds driver, harness, verifier and expected
YAML hashes. Raw logs retain diagnostic timing. All reported filesystem state is
unmodified observation; only owned random directory names and inode numbers are
represented through stable relative names and independently observed equality.
